## 1. 90 秒自我介绍（背熟）

"面试官好，我是李毅，长沙学院计算机科学与技术专业，方向是 AI 应用开发，有 Java 后端基础（Spring Cloud 微服务、MySQL、Redis、RabbitMQ）和 AI 工程化经验。我主要讲一个独立开发的项目——**OpsPilot 智能运维故障诊断 Agent**：它把运维排障的全链路做成了 Agent 流程：告警进来之后自动检索知识库、规划排查步骤、通过 MCP 调用日志和监控工具、把工具结果抽成结构化证据链做校验，最后产出诊断报告并把结论沉淀回知识库。技术上用 LangGraph 编排 Planner-Executor-Replanner 工作流，检索层是 Milvus 向量 + Elasticsearch BM25 双路混合召回并用 RRF 融合，状态用 LangGraph Checkpointer 支持 Memory/Redis/Postgres 三种后端持久化。"

## 2. 项目一页速览（面试开场展示这张）

**一句话**：面向运维告警场景，打通「知识检索 → 任务规划 → 工具执行 → 证据校验 → 诊断报告 → 知识沉淀」全链路。

**技术栈**：Python + FastAPI + LangChain / LangGraph + Qwen + Milvus + Elasticsearch + Redis + PostgreSQL + MCP + SSE + Docker

**链路**：告警接入 → 混合召回 → 计划编排 → 工具执行 → 证据校验 → 报告与沉淀

### 三个"主动暴露短板"的加分点

1. **引用合规率 ≠ 诊断正确率**：前者在数据一致场景天然饱和，对抗场景才暴露真实边界（正确降级率 20%）
2. **Verifier 目前只能校验"引用是否存在"**，不能校验"结论与证据是否一致" —— 这是下一步要做的一致性校验
3. **上下文压缩会偶尔让模型跳过工具调用** → 个别用例退化为安全报告（成本与质量的真实权衡）

## 3. 面试官问题清单（按模块）

### A. 项目总览与动机

**A1. 用一句话说清楚这个项目解决了什么问题？**
> 运维 OnCall 的痛点是"告警来了要靠人查日志、翻文档、凭经验判断"，我把这个过程做成了 Agent 自动化：告警自动进来 → 自动检索历史经验 → 自动调工具取证 → 有证据才给结论 → 结论沉淀回知识库供下次复用。

**A2. 为什么做这个项目？和你后端背景什么关系？**
> 我有 Java 后端背景（微服务、MySQL、Redis、RabbitMQ），日常接触运维场景，知道"排障经验留在人脑里、人一走就流失"这个痛点。选它是因为它天然需要 RAG（知识库）+ Agent（多步工具调用）+ 可靠性设计（不能瞎编根因），正好覆盖 AI 应用开发的核心能力。

**A3. 这个项目你独立做了多久？最难的部分是什么？**
> 分四块推进：检索层（双路召回+融合+评测）、编排层（LangGraph 三节点+护栏）、可靠性层（证据链+Verifier）、成本与观测层。**最难的是"让 Agent 说真话"**——LLM 很容易编一个听起来合理的根因，我最后是靠"工具结果确定性抽取成证据 + 结论必须引用真实证据 ID + 校验不通过就降级"这套机制来约束它。

**A4. 项目上线了吗？有真实用户吗？**
> 诚实说：目前是**可运行的完整系统 + 可复现的评测**，没有真实用户——它跑在我本地的 Docker 全栈里（Milvus + Elasticsearch + Redis + PostgreSQL + MCP 服务 + Mock Prometheus），我用它做了 34 个常规场景 + 10 个对抗场景的可控评测。真实数据接入需要替换 MCP 工具里的数据源。

**A5. 如果让你重构，你会改什么？**
> 三件事：① Verifier 增加"结论-证据一致性"校验（现在是最大短板）；② 把证据链和评测集解耦，让评测能跑在真实告警回放数据上；③ 把工具缓存从进程内换成 Redis，支持多实例共享。

### B. RAG 与混合检索（重点模块）

**B1. 为什么向量检索之外还要加 BM25？**
> 两者互补：向量擅长"语义相近但用词不同"（用户说"服务卡了"能命中"响应缓慢"），BM25 擅长精确 token（告警名 `HighCPUUsage`、指标 `cpu_usage`、错误码）。我实测：关键词型场景纯 BM25 只有 75%，但它在精确匹配上比向量强；纯向量在关键词场景 Recall@1 也有天花板，所以做融合而不是二选一。

**B2. RRF 是什么？为什么不用加权求和？**
> RRF（Reciprocal Rank Fusion）用**排名**而不是分数融合：`score = Σ w_i / (k + rank_i)`，k 默认 60。之所以不用加权求和，是因为向量是余弦/L2 距离、BM25 是无界词频分，**量纲完全不同**，直接加权要先做归一化而容易过拟合；RRF 只看排名，对异常分数天然鲁棒。

**B3. 你的 RRF 权重为什么是 0.7？**
> 测出来的。我做了对照实验：等权（0.5）时关键词场景准确率 87.5%，**比纯向量的 100% 还差**——因为 BM25 的噪声被等权放大了；把向量权重提到 0.7（BM25 占 0.3）恢复到 100%。所以参数不是拍脑袋，是扫出来的。

**B4. 文档怎么切的？为什么这么切？**
> 两级切分：先按 Markdown 标题（H1/H2）切，保留文档结构语义；再按 800 字符递归切分、overlap 100 保证边界不丢语义；最后把 <300 字符的碎片合并（`_merge_small_chunks`），避免碎片化稀释相关性。理由：块太小丢上下文，块太大检索精度下降。

**B5. TopK 怎么定的？**
> 45 题 Golden Set 上扫描：K=1 时 Recall@1 95.56%（有漏召），K=3 起 Recall@3 达 100% 且耗时基本不涨（约 198ms），再往上准确率不再提升、但会引入噪声和 Token 成本，所以选 **K=3** 留召回余量。

**B6. 你的知识库多大？100% 会不会是因为库太小？**
> 这正是我主动暴露的点：知识库 20 篇文档（5 篇告警处置 + **15 篇同类干扰文档**）、41 个分片，**规模确实小**，所以 Recall@3 会饱和在 100%。我给出的口径是：**有区分度的是 Recall@1（向量 95.56% vs BM25 73.33%）和关键词场景的 75%→87.5%→100%**。要更硬的指标，应该把库扩到几百篇、用真实工单做评测集，这是下一步计划。

**B7. 向量库为什么选 Milvus？索引和度量是什么？**
> 选它是因为要服务化、支持持久化和水平扩展，团队可共享；对比 FAISS 是纯库、无服务化。度量要按业务定：我项目里检索层用 langchain-milvus 的默认度量（COSINE），旧的 `vector_search_service` 里是 L2；**换度量必须重建索引**，而且阈值不能跨度量迁移。

**B8. 混合检索失败了怎么办？**
> 有降级链路：ES 不可用或 BM25 召回异常时，捕获异常并**自动退回纯向量检索**，同时在结果 metadata 里标记 `_retrieval=vector_fallback` 便于观测；保证问答不中断。

**B9.（追问）如果两路结果冲突，谁的优先级高？**
> 不设硬优先级，用融合打分解决：RRF 里同时出现在两路且排名靠前的文档自然得分最高；如果某路明显不可用（如 BM25 报错），才走降级。实测等权会让 BM25 噪声拖累结果，所以用权重调节。

### C. LangGraph 工作流与多 Agent

**C1. 为什么用 Plan-Execute-Replan 而不是一个 ReAct Agent 干到底？**
> 运维排障步骤多且**有真实依赖**（先看告警 → 再看日志 → 再对指标），计划先行让过程可解释、可中断、可恢复；每步只执行一个任务，上下文干净，不容易跑偏。代价是多了 Planner/Replanner 的调用（这也是我要做成本治理的原因）。

**C2. Replanner 怎么防止死循环？**
> 三态输出约束（continue / replan / respond）+ 硬护栏：已执行步骤 ≥5 禁止 replan、新计划步骤数不得超过剩余步骤数、总步骤 ≥8 强制出报告。**LLM 再聪明也可能膨胀计划，护栏保证有限步收敛。**

**C3. 你说的"多 Agent"具体是哪几个？怎么协作？**
> 四个角色：① 对话 ReAct Agent（面向人问答）② AIOps 诊断 Agent（Plan-Execute-Replan）③ 知识索引 Agent（切分→向量化→双写 Milvus+ES）④ 告警自动响应 Agent（消费告警→去重→触发诊断）。协作方式：共享同一个知识库和同一套 MCP 工具层，诊断结果通过沉淀服务写回知识库供其它 Agent 复用。

**C4. MCP 是什么？为什么不用普通函数调用？**
> MCP（Model Context Protocol）是工具接入的**协议标准**：工具按协议暴露后可独立部署、跨语言复用，接新系统只改配置不改 Agent 代码。我还做了可靠性：客户端指数退避重试、工具加载失败自动降级为仅本地工具。

**C5. LangGraph 的 State 怎么设计的？**
> 用 TypedDict 定义状态，关键字段用 reducers 控制合并语义：`past_steps` 和 `evidence` 用 `operator.add` 追加（不覆盖），`plan`/`response` 覆盖，还有 `diagnosis`/`verification`/`repair_rounds`/`reliability` 等字段。这样多轮执行的历史和证据能自然累积。

**C6. 条件边是怎么走的？**
> planner → executor → replanner 是主链路；replanner 用条件边决定回 executor（继续/重规划）还是进 diagnose；diagnose 再用条件边决定是回到 executor 补证一轮还是结束。

### D. 证据链与幻觉治理（最能拉开差距）

**D1. 你怎么保证 Agent 不是编的？**
> 核心是**把事实和推理分开**：工具返回后**用规则**（不经过 LLM）抽成 `EvidenceRecord`（工具名+参数+原始片段+evidence_id）；再由 LLM 生成 `StructuredDiagnosis`，每条 `DiagnosisClaim` 必须引用存在的 evidence_id；最后 `Verifier` 逐条校验引用是否真实存在，编造的 ID 会被记录为 `invalid_evidence_ids` 并判该结论不支持。

**D2. 校验不通过怎么办？**
> 分两步：① 生成"补证计划"（依据校验缺口 hints）回到 Executor 补采一轮证据；② 补证后仍不通过，就降级——有结论的标 `hypothesis`，没结论的给安全报告，**报告里明确写"证据不足"**，绝不假装确定。

**D3. 证据覆盖率怎么算的？**
> `coverage = 有有效证据支撑的 claim 数 / claim 总数`；`strict_pass = 所有 claim 都有有效引用`。常规 34 场景覆盖率 100%；对抗场景 90%（有结论的用例仍是 100%）。

**D4. 34 个场景怎么保证可控、可复现？**
> 用 Fixture 注入确定性工具响应：`FixtureRuntime` 用 **ContextVar** 保存当前场景（4 并发互不干扰），把 MCP/本地工具替换成读 fixture 的工具；每个用例定义告警内容、各工具返回值、期望结果。这样跑多少次结果都一致，不依赖真实监控。

**D5. 那 100% 通过率是不是口径太松？**
> **要区分两个口径**：引用合规率（结论是否引用了存在的证据）在数据一致的常规场景天然接近 100%，它证明的是"机制有效"；**诊断正确性**要用根因正确率衡量，我在 10 个对抗场景里实测只有 20%——因为 Verifier 只查引用存在性，不查"这条证据是否支持这个结论"。这个短板是我主动测出来的，改进方案是在 Verifier 增加一致性规则（结论里的关键数值/实体必须在被引用证据原文中出现）。

**D6.（追问）如果模型就是引用了错误证据呢？**
> 这正是现在的能力边界：它能保证"引用的证据真实存在"，但不能保证"引用的证据能推出该结论"。冲突场景实测 5 例中 4 例被误判为已验证。要彻底解决需要两步：一致性校验（数值/实体核对）+ 让 LLM 在冲突证据下显式输出"证据冲突"而不是硬选一边。

### E. 成本治理与观测

**E1. 你怎么降 Token 的？**
> 三条链路：① **工具结果缓存**——按 `tool_call_fingerprint`（工具名+参数哈希）缓存，同一次诊断里重复调用直接复用；② **上下文压缩**——进入 LLM 的文本按配置截断，**但证据链始终用原始返回**，所以压缩不影响校验；③ **Token 预算**——`ReliabilityState` 维护估算 Token，超预算输出部分报告。

**E2. 降了多少？代价是什么？**
> 同 12 个用例 A/B：平均 Token 25,345.7 → 17,471（**-31.1%**），耗时 82.79s → 63.84s（**-22.9%**）。代价是 1 例因为压缩后模型跳过工具调用退化成安全报告（覆盖率 100% → 91.67%）——**这就是真实的成本-质量权衡**，我在简历里如实写了。

**E3. 缓存怎么保证不串数据？**
> key 是"工具名 + 参数"的哈希，参数不同就不会命中；评测里每个用例开始会 `clear()` 隔离；生产上如果换 Redis 做共享缓存，需要加 TTL 和按会话/租户隔离前缀。

**E4. Langfuse 用来做什么？**
> 全链路观测：用 CallbackHandler 追踪模型调用、工具调用和执行链路；再用 `RunMetricsCollector` 汇总节点数、Token、时延、缓存命中与校验结果，输出 JSON/Markdown 报告。**未配置 Langfuse 时自动降级**，不阻塞主流程。

### F. 持久化与工程化

**F1. 会话状态怎么存的？**
> LangGraph Checkpointer 按 `thread_id` 持久化，支持三种后端一键切换：MemorySaver（本地开发）/ Redis Stack / AsyncPostgresSaver（生产），Postgres 首次启动自动建表。对话和 AIOps 用不同 `thread_id` 前缀隔离，互不覆盖。

**F2. 为什么 Redis 要用 Stack 版本？**
> `langgraph-checkpoint-redis` 依赖 RediSearch（要用 `FT.INFO` 建索引），普通 redis 镜像不支持；另外图是异步执行，必须用 **Async 版 saver**——同步版在异步图上会直接 `NotImplementedError`，这是我踩过的坑。

**F3. 数据库挂了会怎样？**
> 自动降级：Postgres 不可用时回退 MemorySaver，服务不中断，只是重启后丢会话；同时有 `/health` 探活，Milvus 挂了健康检查直接返回 503。

**F4. 部署怎么做的？**
> Docker Compose 一键全栈：Milvus + Elasticsearch + Redis + PostgreSQL + 2 个 MCP Server + Mock Prometheus + FastAPI；配置全部环境变量化（融合方式、记忆后端、重试策略都能开关）。Windows 也有一键脚本。

**F5. 测试怎么做的？**
> 三层：pytest 单测（融合算法、告警解析、Checkpointer 后端、证据链）/ 集成测试（health、上传、检索，环境缺失自动 skip）/ 评测脚本（RAG Recall@K、混合检索四模式对比、34 场景可控评测）。

### G. 基础知识（必问）

**G1. RAG 的完整流程？**
> 离线：文档 → 切分 → Embedding → 向量库；在线：query → Embedding → 召回（向量/关键词/混合）→ 融合与截断 → 拼上下文 → LLM 生成 → 引用来源。进阶是 query 改写、重排（rerank）、阈值过滤、多路融合。

**G2. RAG 和微调怎么选？**
> 知识频繁变、要求可溯源、数据敏感不能用外部 → RAG；风格/格式要求稳定、领域术语理解差、延迟要求高 → 微调。成本上 RAG 增量更新便宜，微调每次改数据都要重训。实际项目多是 RAG 为主 + 微调/提示词调优。

**G3. 向量检索的相似度度量有哪些？**
> 余弦相似度（看方向，文本常用，归一化后 0~1）、内积（IP，配合归一化等价余弦）、欧氏距离 L2（看绝对距离，越小越相似）。**换度量或换 Embedding 模型都必须重建索引**。

**G4. ReAct 和 Plan-Execute 的区别？**
> ReAct 是"思考-行动-观察"的循环，边想边做，灵活但过程不可预期；Plan-Execute 先出完整计划再逐步执行，可解释、可中断恢复，但计划错了要重规划。我项目里对话用 ReAct（自由问答），诊断用 Plan-Execute-Replan（多步有依赖）。

**G5. Function Calling / Tool Calling 的原理？**
> 把工具的 JSON Schema 一起发给模型，模型返回结构化的 tool_call（函数名+参数），运行时执行后把结果作为工具消息回灌，模型再决定继续调工具还是给最终答案；循环直到没有 tool_call。

**G6. 结构化输出怎么保证？**
> 用 Pydantic 定义 Schema，通过 `with_structured_output` 约束模型输出为 JSON；再在代码侧做校验（我项目里 Verifier 就是校验结构化诊断的引用完整性）。**不要用正则解析自由文本**，不稳定。

**G7. 幻觉怎么治理？**
> 四层：① 提示词约束（禁止编造、无证据要说不知道）② 检索约束（只基于召回内容回答）③ 结构化输出 + 程序校验（我项目的证据链）④ 兜底降级（证据不足输出安全报告）。我项目里第 ③ 层是核心差异化。

**G8. SSE 和 WebSocket 怎么选？**
> SSE 是单向（服务端→客户端）、基于 HTTP、自动重连、实现简单，适合 LLM 流式输出；WebSocket 双向、适合需要客户端持续交互的场景。我项目对话和诊断都用 SSE（`sse-starlette` + `EventSourceResponse`）。

### H. 智学在线教育平台项目（第二个项目，别被问倒）

**H1. 那个项目你用 Spring AI 做了什么？**
> 对接阿里云百炼千问 Max，做课程咨询、推荐、购买的智能助手：用 **Tool Calling** 把大模型和既有微服务打通（查课程、下单、查积分），用 **RAG** 提升回复准确率。重点是"AI 能力嵌入既有业务系统"，不是另起一套。

**H2. Tool Calling 和你的微服务怎么整合的？**
> 把微服务接口封装成工具（函数名+参数+描述注册给模型），模型返回 tool_call 后由后端调用对应微服务，再把结果回灌给模型生成最终回复；要注意工具的幂等性和鉴权（不能让模型随便下单）。

**H3. 优惠券领取为什么要用 Lua 脚本？**
> 领券是"判断库存 → 扣减 → 记录用户"三步，非原子操作在并发下会超卖；用 Redis + Lua 把判断和扣减放在一次原子执行里，配合 Redisson 分布式锁做兜底，保证库存不超卖。

**H4. RabbitMQ 在那里解决什么问题？**
> 非核心链路异步解耦（如发券通知、积分累计、消息推送），通过手动 ACK + 死信队列保证可靠投递，核心下单链路只做必要同步操作，降低 RT。

**H5. Redis 缓存怎么防穿透/击穿/雪崩？**
> 穿透：空值缓存 + 布隆过滤器；击穿：热点 key 加互斥锁/逻辑过期；雪崩：过期时间加随机抖动 + 多级缓存。项目里学习进度、点赞、积分这类高频写用"Redis 缓存 + 异步持久化"。

## 5. RAG 召回过滤阈值专题（你问的那个问题）

### 5.1 是什么

召回阈值（score / similarity threshold）是**在召回结果里再做一次相关性过滤**的超参数：只有分数优于阈值的片段才进入上下文。工程上通常和 TopK 一起用：

```
候选（TopK 更大，例如 10）→ 阈值过滤 → 至少保留 min_results 条 → 拼上下文
```

### 5.2 不同度量的阈值含义完全不同（这是最容易答错的地方）

| 度量 | 取值范围 | 方向 | 典型阈值 | 注意 |
|---|---|---|---|---|
| 余弦相似度（归一化） | 0 ~ 1 | 越大越相似 | 0.6 ~ 0.85 | 最常用；跨模型不可迁移 |
| 内积 IP | -∞ ~ +∞ | 越大越相似 | 需按模型标定 | 归一化后≈余弦 |
| 欧氏距离 L2 | 0 ~ +∞（归一化后 0~2） | **越小越相似** | 0.8 ~ 1.2 | 方向相反，别写反 |
| BM25 分数 | 0 ~ +∞，随 query/语料变化 | 越大越相关 | **不宜用绝对阈值** | 建议用"Top1 分数的百分比"做相对阈值 |
| RRF 融合分 | 约 (0, 1/(k+1)] × 路数 | 越大越好 | 不直观 | 融合后建议只取 TopK，不设绝对阈值 |

**一句话**：阈值必须绑定"度量 + Embedding 模型 + 语料"，没有放之四海皆准的数字。

### 5.3 阈值解决什么问题

1. **抑制幻觉**：把不相关片段塞进上下文，是 LLM 编造答案的主要诱因
2. **省 Token**：少送无关片段，直接降本（你项目 Token 已经是关键指标）
3. **提升精度**：避免"看起来相关但实际无关"的片段挤掉真正有用的片段
4. **可观测性**：低分占比可以当作知识库覆盖不足的信号（该补文档了）

### 5.4 怎么科学地定阈值（面试就这么答）

1. **先看分数分布**：在 Golden Set 上把每个问题的 Top1/Top3 分数打出来，画直方图。如果相关与不相关形成"双峰"，**谷底就是天然阈值**
2. **扫阈值看指标**：阈值从 0.3 扫到 0.9，记录 Recall@K 与 Precision（或"回答正确率"），取**召回不明显下降、精度明显上升**的那个点
3. **设置下限兜底**：无论阈值多高，**至少保留 1~2 条**（`min_results`），避免全被过滤导致"没有检索到内容"
4. **相对阈值兜底（针对 BM25）**：例如"保留分数 ≥ Top1 × 0.5 的结果"，避免语料变化导致绝对阈值失效
5. **回归验证**：阈值上线后用同一个 Golden Set 回归，确认没有把原来答对的题过滤掉

### 5.5 你项目现在的情况 + 建议怎么加

**现状**：目前只用 TopK=3，**没有做分数阈值过滤**（`hybrid_search_service` 里按 RRF 分数排序取前 K，没有阈值参数）。所以面试被问到时别硬说"有阈值"，可以这样答：

> "目前是 TopK 截断，没有做阈值过滤——因为小知识库上分数分布比较集中，阈值收益不明显。如果要加，我的设计是三个参数：`VECTOR_SCORE_THRESHOLD`（余弦相似度，先按 0.6 起扫）、`BM25_RELATIVE_RATIO`（相对 Top1 的 0.5）、`MIN_RESULTS`（兜底 1 条），然后在 45 题 Golden Set 上扫阈值画 precision/recall 曲线定值。"

**如果要落地（改动很小，我可以直接实现）**：

```bash
# .env 新增
RAG_SCORE_THRESHOLD=0.6      # 向量相似度阈值（0 表示不过滤）
RAG_MIN_RESULTS=1            # 至少保留条数
RAG_BM25_RELATIVE_RATIO=0.5  # BM25 相对 Top1 的比例阈值
```

在 `hybrid_search_service.search_with_details()` 里，融合排序后先按阈值过滤、再用 `MIN_RESULTS` 兜底，最后取 TopK；同时在返回的 metadata 里记录 `_filtered_by_threshold` 便于观测和评测对比。

**验证方式**：改完用 `python scripts/eval_recall.py` 跑一遍，对比过滤前后的 Recall@3 与平均 Token——**如果 Recall 不掉而 Token 降了，阈值就是有效的**；如果 Recall 掉了，说明阈值太严。

### 5.6 面试高频追问

**Q：阈值设太高会怎样？** → 召回不足，模型"没材料可用"，会出现"知识库中没有相关内容"的回答变多，甚至漏掉正确答案；所以必须有 `min_results` 兜底。

**Q：能不能给个通用值？** → 不能。余弦相似度阈值在 0.6~0.85 之间是常见起点，但必须用**你自己的 Embedding 模型 + 语料**标定：同一个阈值换模型（如 text-embedding-v4 → qwen3.7-text-embedding）就失效，因为分数分布整体平移了。

**Q：有了 RRF 还需要阈值吗？** → 两者不冲突：RRF 决定**排序**，阈值决定**截断**。RRF 分数本身不适合做绝对阈值（它只反映排名），所以实践中常见做法是"RRF 排序 + 对原始向量相似度做阈值 + min_results 兜底"。

**Q：阈值和 TopK 一起怎么配？** → 先放宽 TopK 多召回（如 10），再用阈值收紧，最后保留 min_results；这样比"直接小 TopK"更可控，因为阈值是相关性判断，TopK 是数量限制。
